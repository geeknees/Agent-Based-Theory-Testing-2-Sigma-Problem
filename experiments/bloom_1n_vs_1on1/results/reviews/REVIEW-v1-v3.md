- v1: 教室条件 と 一対一条件 の2条件

3. 何が分かったか: メモリーが無限だと天井効果再現する、ルールは伝えていなかった

- v1: メモリーに上限がなかったため、講義の内容がほぼそのまま複写されて天井になった
- v2: それに加えて、タスクプロンプトそのものにルールが渡されため、別経路でも天井になった
- v3: 評価タスクの定義そのものをlearner_prompt(学習者に見せる、ルールなし)とhidden_rules(採点者だけが見る)に分けた、初めて条件間の差が出た

4. 何が言えないか: 学習効果の差の検証などは後まわし
5. 次に何をすべきか: 学習効果の差の検証について実装に入る

## チェックリストへの追記候補

- **`evaluation_tasks.prompt` 列の値は task_id が世代をまたいで再利用された場合、実際に solver へ送られたプロンプトと一致しないことがある。**
  発見経緯: masumi の l5_counterexample_01 目視確認をエージェントが `et.prompt` で裏取りしようとしたところ、
  ルール同梱の v2 スタイル文面が出た(v3 は `learner_prompt`/`hidden_rules` 分離構造のはず)。
  調査の結果、`evaluation_tasks` は `task_id` PRIMARY KEY + `INSERT OR IGNORE` のため、
  同一 task_id(`l5_counterexample_01`)を v2(run `4b1ac552`, 05-14 09:18)が v3 より先に挿入しており、
  以降の run(v3 以降すべて)の再挿入は無視され、**`prompt` 列は永久に v2 時点の値のまま**になっていた。
  実際に solver へ渡ったのは `eval_tasks_v3.json` の `learner_prompt`(ルールなし、JSON ファイルから都度読込)であり、
  スコア計算には影響しない(スコアは `evaluations.score_json` 由来で `et.prompt` を再パースしていない)。
  開発ログ「問題2」(JOIN 条件の run_id 混在)と同根(task_id が run をまたいで共有される設計)だが別の症状。
  → プロトコル付録Aに `et.prompt` 直読みクエリを追加する際は「複数世代で再利用された task_id は不正確な場合がある」の
  注記を必須にする。他世代(v4 以降、task_id 命名が変わらず再利用されている l1_recall_01 等)への影響範囲は未調査
  (ただしスコア集計ロジックは `et.prompt` に依存しないため、査読前チェックで検証済みの数値には影響なしと推定)。
